# PATCH//AGENCY: workplace concept learning audit and handoff

**For Claude to continue:** read this before changing lessons, labs or Agency shifts. This is an evidence-led audit and implementation brief, not a request to deploy. Keep all work on `preview`; do not touch production or infrastructure.

## Goal

When an alert teaches a concept, let learners see that concept operating in a believable workplace example. A learner should be able to move from “I found this in the evidence” to “I understand what the system is doing” without losing their place in a shift.

Do not add a link to every alert. Add a short, optional **See it at work** interaction where a visual or hands-on example makes a difficult concept easier to understand. Keep incident evidence, decisions and response as the main task.

## Audit scope and evidence

Reviewed all four `content/agency/shift-*.json` files (20 alerts), all 29 entries in `content/lessons.json`, all 44 entries in `content/labs.json`, the Agency UI in `static/js/agency/ui.js`, lesson/lab routing in `src/app/06-learn.js` and `src/app/07-labs.js`, and the Agency pilot design in `docs/agency-pilot.md`.

The shifts already contain substantial, useful evidence and teaching: guided hints, searchable logs, evidence citations, a model handover and Shadow mode. Existing visual assets include lesson diagrams for phishing, ransomware, identity/MFA, SQL injection, XSS, SOC/log triage and networking, plus focused evidence labs for sign-in spray, endpoint process trees, ransomware timelines, SQLi, XSS, IDOR and cloud bucket access.

The gap is the bridge between those materials and the shift. The shift runtime does not render contextual lesson/lab links from its `lessons` metadata. That metadata is broad topic and exam mapping, not a per-alert teaching link. The client file does not preview concepts. A direct route change during a shift is also unsafe UX: the active shift is not saved part-way and leaving can restart it. Preserve the work-in-progress when adding learning links.

The wider site review found a good reuse base but uneven visual coverage: 8 of 29 lessons contain a step-through flow diagram; 44 labs each map to a lesson, including realistic evidence views for wireless scans, logins, processes, web requests and cloud policies. Several topics already have a clear concept visual plus a practice lab (identity/MFA, phishing, SQLi, XSS, ransomware, SOC), while VPN behaviour has no dedicated visual, IDOR lacks a lesson diagram, and cloud's current visual practice is primarily policy/log evidence. The right direction is to connect existing experiences first and add new visuals only for concepts where a learner needs to see a system change state. Do not turn every short lesson into a diagram by default.

## Recommended implementation

1. **Define a small per-alert teaching map** in the shift data, separate from broad `lessons` exam/topic metadata. Each entry should name the alert, the concept, an existing or planned learning component, a short outcome and whether it is available now. Do not duplicate long lesson copy in shift JSON.
2. **Create a reusable, accessible in-shift explainer surface** in `static/js/agency/ui.js`: a clearly labelled, optional “See it at work” disclosure or dialog tied to the selected alert. It must not navigate away, advance the shift clock, change the alert result, or lose findings. If a full lesson link is also offered, open it in a new tab and label that behaviour; keep the shift tab intact. Test keyboard focus, close/return behaviour, mobile layout and screen readers.
3. **Build the first explainer for shift-01 impossible travel and VPN egress.** This is the clearest concrete example requested by the owner and the lesson currently lacks a VPN visual. Use a toggle, simple route/map and log snippets to show physical location vs public egress. Include VPN on/off, full-tunnel vs off, why multiple users share egress, and what a real impossible-travel investigation still checks. Keep assumptions and simplifications visible.
4. **Add the next high-value explainers in this order:** shift-02 repeated MFA prompts and malicious inbox rule; shift-04 IDOR and cloud permissions; shift-03 combined compromise/data-theft/backup timeline. Reuse existing lesson diagrams and labs before inventing new content.
5. **Add contextual links to existing learning assets** for the remaining alerts (SSH/scan, sign-in spray, malware-tree, ransomware-timeline, SQLi/XSS, email/header tools). Make these optional, specific (“See how a VPN changes sign-in location”), and never render a generic pile of topic links.
6. **Keep the site-wide relationships current as implementation proceeds.** The audit has already inventoried all lessons and labs; as new scenarios land, check each lesson and evidence lab for a real-world counterpart in missions, Agency shifts, career simulations and news/CVE explainers. Record each relationship once in structured metadata and check for stale/broken routes. Keep current Wi-Fi attack gaps (deauthentication, evil twin, WPS PIN) visible as separate content work; don't force them into SOC shifts unless a scenario genuinely demonstrates them.

## Acceptance criteria for Claude

- Every alert in all four shifts has been reviewed and recorded as: existing visual/lab to link, a justified “no new visual” decision, or a prioritised gap.
- The impossible-travel alert has a working interactive VPN on/off visual showing egress-location changes while physical location stays fixed, plus accurate limits and false-positive guidance.
- The MFA, inbox-rule, IDOR and cloud-permission gaps above have either shipped a safe prototype or are explicitly sequenced with an estimate and dependencies.
- The learner can open/close an explainer without losing the current shift, alert selection, evidence findings or clock state. No concept activity makes live network requests or accepts real credentials/customer data.
- Diagrams and micro-interactions use fictional data, work with keyboard and screen reader, fit 390 px, respect reduced motion and dark/light themes, and state what is simplified.
- Add regression coverage for each new data mapping, route and interactive state. Run the required Python and JS suites, offline build, Agency smoke journeys and browser check at desktop and phone widths. Inspect CI before merging.
- Record implementation commits, verification results, preview link and any remaining risks here. No production deployment or infrastructure changes without explicit owner approval.
